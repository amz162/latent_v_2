  1259→Notes — judgment calls where the same textual pattern is harmless in one script but leaky in another:
  1260→
  1261→1. `.fillna(0)` is HARMLESS when applied to FEATURE columns (RSI/volatility/sma-ratio/returns/atr/bb_width/lag-features) but LEAKY when applied to TARGET columns (target_5d/10d/21d, tp1_before_sl_5d). Example: train_all_with_backtesting.py:30-49 fillna(0) on bb_width/atr_14/return_*d/volatility_14d = HARMLESS_FEATURE_FILLNA; train_all_with_backtesting.py:52 (in add_labels) fillna(0) on target_{hz}d would have been LEAKY but Task 46 already removed it.
  1262→
  1263→2. `StandardScaler().fit_transform(f)` is LEAKY when fit on the FULL per-stock history BEFORE splitting (e.g., train_all_with_backtesting.py:198 train_cnn_lstm, train_cl_tier.py:237 train_gru, train_multi_horizon.py:137 train_lstm, train_remaining_models.py:97,147) but HARMLESS (HARMLESS_PREDICT_TIME) when fit on the most-recent SEQ bars at LIVE-PREDICT time inside a `predict_fn(sdf)` closure (e.g., train_all_with_backtesting.py:178, 224, 269 — the live inference path that doesn't feed back into training). The same textual line `sc=StandardScaler(); fs=sc.fit_transform(f)` means two different things depending on whether `f` is the training history or the live-inference SEQ bars.
  1264→
  1265→3. `df["close"].shift(-h)` WITHOUT groupby is HARMLESS (per-stock) when called on a PER-STOCK df inside a per-stock load loop (e.g., train_all_models_db.py:49 inside add_labels called per-stock from L365, train_all_db.py:55 inside add_labels called per-stock from L72, train_cl_tier.py:52, train_multi_horizon.py:59, train_remaining_models.py:56, train_tier2_foundations.py:86, walk_forward_backtesting.py:65, improve_models.py:45 — all called per-stock inside their load() functions). The SAME textual pattern is LEAKY (cross-stock) when called on a CONCATENATED multi-stock df — e.g., fix_predictions_and_backtest.py:206 inside train_chronos_analog receives the concatenated df from main L853, so `shift(-hz)` without groupby crosses stock boundaries. The fix in both cases is the same: use `ml_integrity.add_forward_returns(df, …)` which always uses `df.groupby(symbol)[close].shift(-h)` regardless of whether df is per-stock or concatenated.
  1266→
  1267→4. `df.groupby("symbol")["close"].shift(-h)` (with groupby) is ALWAYS safe from cross-stock leakage (whether df is per-stock or concatenated) — e.g., retrain_all_361_stocks.py:341, train_all_optimized.py:144-146, backtest_all_models.py:268-269, ml_integrity.py:44. The only remaining concern is the .fillna(0) that may follow it (retrain_all_361_stocks.py:341 still has fillna(0) → LEAKY_TARGET; train_all_optimized.py:144-146 has no fillna → ALREADY_FIXED).
  1268→
  1269→5. `split=int(len(sdf)*0.8)` is HARMLESS_OTHER when `sdf` is ONE STOCK (per-stock chronological split for a per-stock model — e.g., train_all_db.py:73, train_all_models_db.py:66/123/136/185, retrain_all_361_stocks.py:210/278) but LEAKY_SPLIT when `df` is the CONCATENATED multi-stock df and the rows are NOT globally date-sorted (e.g., improve_models.py:138, train_multi_horizon.py:88, train_remaining_models.py:188, train_cl_tier.py:155, train_tier2_foundations.py:269 — these scripts concatenate per-stock dfs in stock order without a global date sort, so the 80% row boundary lands inside one stock's history, mixing train/test across stocks). The same pattern is LEAKY_SPLIT (minor) even when the concatenated df IS date-sorted (train_xgboost.py:213, train_multi_models.py:179) because a single date's rows can straddle the boundary.
  1270→
  1271→6. `purged_stock_folds` (by-symbol K-fold) is LEAKY_SPLIT in train_cl2_tier.py:694, train_cg_model.py:451, train_pi_tier.py:198 because the same calendar dates appear in train and validation across correlated stocks (cross-sectional CV, not time-OOS) — this is the leak that audit_cg_model.py was created to identify and fix.
